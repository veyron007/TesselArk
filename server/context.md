# Server context

- `index.js` starts Express on loopback at `PORT` (default 3001) and serves a built `dist/` SPA from the same origin when present. `api.cjs` exports `createApp({ db })` for tests; `db.cjs` opens and seeds SQLite. Finance, returns, return tax review, orders, batch inventory, evidence, local statement import, workflows, and statutory simulation routes live in their own modules and are registered by these shared files.
- The legacy `/api/simulations` GST-return path requires every branch grant for its GSTIN, including idempotent replays; list responses hide whole-registration GST-return simulations from partially scoped users while still showing their permitted invoice simulations.
- `ERP_DB_PATH` selects the persistent database; default is `server/erp.sqlite`. Tests use `:memory:`. Schema creation and named synthetic demo fixtures are idempotent. The Bengaluru prior-month fixtures include two approved sales, a partial bank payment, an approved return, and a draft return. A separate prior-month Mumbai sale, partial payment, and approved return populate the default Finance and Returns scope. Its GST period is locally approved with an explicit internal-demo note for simulator testing; it has no official filing evidence. Current-month GST periods stay open. Linked stock movements and tax proposals reconcile. Demo fixtures may be added to an existing local demo DB on restart.
- All API money is integer paise (`*Cents`), quantities are whole units, GST rates are basis points (`1800` means 18%). Invoice line tax rounds once per line. This is a demo calculation, not a statutory tax engine.
- The runtime server requires an explicit `ERP_AUTH_MODE=demo` or `ERP_AUTH_MODE=production`; `npm run dev` sets demo mode for local work. Demo mode uses `x-company-id` and `x-user-id` selectors. These headers are demo impersonation. Production mode ignores them, requires an explicitly provisioned credential and an opaque SQLite-backed `__Host-erp_session` HttpOnly cookie, and derives company/user identity on the server. Both modes bind only to loopback. There is no automatic credential for seeded demo users. Provision an existing user by setting `ERP_DB_PATH`, `ERP_AUTH_USER_ID`, `ERP_AUTH_EMAIL`, and `ERP_AUTH_PASSWORD` in the environment and running `node server/auth-provision.cjs`; reprovisioning revokes that user's sessions. Use a private HTTPS reverse proxy because production cookies are Secure; do not expose the app directly to the internet without a deployment/security review.
- Production auth routes are `POST /api/auth/login` (JSON email/password, returns CSRF token and session cookie), `GET /api/auth/session` (returns current user and the same per-session CSRF token), and `POST /api/auth/logout` (requires CSRF, revokes session). Other unsafe `/api` methods require `X-CSRF-Token`. Sessions expire after eight hours. Login attempts are limited in SQLite by email and client IP; general API requests are rate-limited in process by client IP. Set `ERP_AUTH_TRUSTED_PROXY_IPS` to a comma-separated list of numeric IP addresses for trusted direct reverse-proxy peers; the proxy must overwrite or append `X-Forwarded-For` with the actual client IP. Without it, all clients behind one proxy share an IP limit. In-process API limiting is not shared between server processes and still needs a deployment-level limiter. Grant checks remain live per request.
- Invoice status is draft → submitted → approved. Only approval posts stock movements and enters GST period totals. Tracked goods reject insufficient stock; service items skip stock. Sale approval and manual issues allocate dated batch stock using FEFO before unbatched stock, posting paired physical and batch movements atomically. An item's stock-tracking setting cannot change after stock, order, or invoice history. Invoice creation snapshots the counterparty name/GSTIN so historic views survive master edits. Approved purchases prevent duplicate supplier invoice references. Manual stock movements accept an optional `clientReference` for idempotent retries.
- An invoice may supply `fulfillmentId` for one confirmed order receipt or dispatch. Scope, type, party, exact item/quantity/price/GST lines, and posted fulfillment movements are checked; one fulfillment can link to one invoice. Linked invoice approval records GST/accounting effects and does not post stock again. Two synthetic prior-month Bengaluru orders are partially fulfilled and linked to sale/purchase invoices; remaining quantities and stock balances reconcile.
- Approved purchases appear in `/api/gst/purchase-evidence`. A local accountant can compare against synthetic imported 2B fixtures, then mark matched evidence eligible or block with reason. `eligibleItcCents` sums only matched and locally approved evidence by `claimPeriod` (fixture source period). `purchaseTaxCents` is raw recorded tax. `payableEstimateCents` and `surplusReviewedCreditCents` are local arithmetic, with no tax-head utilization or statutory liability determination. Reviewed periods reject later invoice approval and evidence changes; unresolved purchases or submitted invoices block review.
- Approved return-note tax proposals have their own accountant decisions and audit in `/api/return-tax/reviews`; `/api/return-tax/preview` shows local adjustment arithmetic. These decisions do not change recorded GST period totals, eligible ITC, or official filing state.
- Five synthetic workflow specimens populate the default company context across manufacturing, pharmacy, payroll, and CA notice review. Draft, submitted, and locally approved examples have event history and synthetic evidence references. They are generic prototype records and do not create specialist effects.
- The default Mumbai Evidence Library includes one tiny plain-text synthetic pharmacy workflow attachment with a locally reviewed first version and a pending second version. Both files state that they are presentation specimens, not authentic supplier records. The seed is idempotent on database reopen.
- No GST portal integration, official verification, filing, or GST component split is implemented. The production auth API and sign-in UI do not make this demo production ready; the current data is synthetic and public HTTPS deployment has not been verified. Local period approval must never be labeled filed.
- Balanced source-linked invoice/payment journals, local bank statement reconciliation, cashier sessions and operational reporting are installed separately. Seeded approved sources backfill journals idempotently; new invoice approvals and payments post in the caller transaction. Zero-value approved invoices retain zero-value journal source history. Explicit accountant return settlement posts approved commercial subtotal once to AR/AP and contra sales/purchases; tax proposals, inventory valuation and opening balances do not yet post to books.
- Cash sale receipts in Finance require an open cashier session for that invoice branch and payment date and are assigned atomically. Cash supplier payments are held until a linked payout/allocation path exists. A closed drawer date cannot accept new receipts or another session.
- Newly approved tracked sales returns create source-movement/lot-linked quarantine receipts rather than immediately increasing saleable stock. Inspection release posts physical and batch stock once; rejection retains unsaleable status. An idempotent synthetic default-DB specimen `DEMO-CRN-MUM-QA-001` demonstrates this, while pre-existing approved return movements are retained as legacy records.
- Run `npm test` from the repository root for the HTTP integration tests in `server/tests`.
- `locations.cjs` adds scoped warehouse/store/rack records, classification of already-posted unbatched stock, and same-GSTIN dispatch/receipt with in-transit balances and idempotent references. Inter-GSTIN dispatch is blocked because tax and transport documents are not implemented. Batch-level location tracking is not yet connected.
- `conversion.cjs` records reviewed exact-ratio stock conversion and posts source issue/target receipt once; entered cost basis remains documentary and does not affect valuation or the ledger. `catalogue.cjs` adds audited company curation and sourced alternatives with no medicinal equivalence claim. `counts.cjs` adds physical snapshots, independent variance review with replay-safe stock adjustments, and demand-based replenishment proposals; proposal reviews do not create purchase orders.
- `pricing.cjs` adds dated advisory price rules, precedence and independently reviewed exceptions; there is no order/invoice pricing hook. `credit.cjs` computes scoped customer exposure, base policy and time-limited reviewed extra credit. Hold blocks new over-limit sale order confirmations and sale invoice submissions atomically; warn remains advisory.
- `consignment.cjs` separates custody and ownership, with unsold returns and reviewed settlement proposals but no automatic sale, tax or ledger documents. `price-adjustments.cjs` captures approved-invoice rate differences and independent commercial/tax review without rewriting invoices or posting GST. `supplier-comparison.cjs` normalizes quotes, free packs, tax assumptions and freight with approved purchase history, then records an independently reviewed choice without creating a PO.
- `bundles.cjs` versions bundle formulas, previews stock and reviewed schemes, and reads source deal history without posting documents. `budgets.cjs` keeps expense budgets, sales/collection targets and reviewed source allocations separate. `order-crm.cjs` links customer follow-up cases to the exact sale order with immutable commitments and blockers, without changing order posting.
- `document-output.cjs` saves immutable scoped invoice print snapshots with source/template version and local-language labels; text item identity is not a validated scannable barcode. `delivery.cjs` links confirmed sales dispatches to partial staff-reported handover attempts; collection reports remain documentary and unallocated. `master-import.cjs` previews and commits company-wide item-master CSV rows with source audit and replay checks; it never posts stock or invoices.
- `migrations.cjs` has a versioned baseline marker for the existing schema and checks migration file hashes. Apply it with the explicit offline `db:migrate` command and a separate backup path. Historical schema creation and conditional alters still live in `db.cjs` and module installers; this transitional baseline does not make startup schema changes versioned. `sqlite-maintenance.cjs` snapshots WAL-aware backups and stages verified restores in the destination directory.
